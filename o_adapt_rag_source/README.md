# O-Adapt - RAG-grounded Orienteering Course Generator

PE6201 individual project prototype for Jurong Central Park. Enter a target distance, difficulty, 3-5 intermediate controls and training focus. The system retrieves relevant policies, enumerates routes that pass hard constraints, and asks an OpenRouter model to select the final route from that validated set. A fixed template summarises the selected structured result.

The interface has two control-source modes. **Existing controls** chooses from the supplied eligible records. **Generate new positions** deterministically proposes virtual `GPxx` GPS controls on verified path-network nodes. These points do not require physical flags or distinctive features: the map guides the runner to their coordinates. GPS accuracy and temporary site conditions remain limitations.

After generating a route within the verified path scope, including a virtual-control route, the optional **Activity Tracking** panel can record the user's GPS trace and sequential control arrivals. It requires two consecutive readings within 20 m at 25 m accuracy or better. Activity data stays in browser storage and can be deleted or exported as JSON or GPX; it is never sent to the server.

## Run

Node.js 20+; no `npm install` required.

```sh
npm start
```

Open http://localhost:3000. Press Generate to produce a route. No model call occurs on page load. Because the final route is model-selected, a missing key produces an explicit failure instead of silently substituting a deterministic route.

To record an activity, generate a route that passes the project checks, select **Start activity**, and allow browser location access. Keep the page open during the activity. The next existing or virtual control is confirmed automatically after two qualifying nearby readings. Select **Stop** to end early, then export JSON or GPX if needed. Geolocation works on localhost; a deployed copy must use HTTPS.

For real model route selection, copy `.env.example` to `.env` and configure `OPENROUTER_API_KEY` locally. Default model: `openai/gpt-4o-mini`. Restart the server after changing `.env`. Never commit or share the key.

## Verify

```sh
npm test
npm run evaluate
npm run evaluate:explore
npm run evaluate:route-human
```

`npm test` checks policy retrieval, field-verification gates, exclusions, invalid input, deterministic output, GPS arrival confirmation and GPX export, a stubbed model adapter and local HTTP responses. It temporarily listens on port 3137 and spends no API credit.

`npm run evaluate` runs the 30 cases frozen in `evaluation/cases.json`, records the fixture SHA-256 and writes actual results to `evaluation/results.json` and `evaluation/RESULTS.md`.

`npm run evaluate:explore` separately runs the 10 exploration cases in `evaluation/explore-cases.json`. It checks that virtual `GPxx` controls lie on graph nodes I verified, meet distance and spacing constraints, pass the recorded verification gates and abstain on invalid or unavailable inputs. The separate activity tests check GPS arrival logic.

Recorded offline results: 17/20 verified courses, 3/20 generation abstentions and 30/30 expected-behaviour checks. **The original target of 16/20 verified complete passes is achieved for the dataset I verified.**

Recorded exploration results: 6/6 normal requests produced constraint-valid virtual `GPxx` routes on graph nodes I verified, and 4/4 edge cases abstained. Physical control features are unnecessary because the runner navigates to the coordinates using GPS.

Recorded final-architecture live results: 17/17 model route selections succeeded and passed all deterministic contracts. Fifteen selected routes differed from the deterministic top candidate. The batch used 37,750 tokens at a provider-reported cost of US$0.00602205, with 1.74-second average model latency. See `evaluation/live/ROUTE_LIVE_RESULTS.md`. An earlier explanation-only A/B experiment is retained as iteration evidence, not as the final product evaluation.

A separate 20-request set generated by Gemini 2.5 Flash and frozen before route evaluation yielded 18 routes; all 18 passed the recorded objective checks. Gemini then blindly compared the 10 model-selected routes that differed from the deterministic baseline: selected 3, baseline 4, ties 3. Its mean training-focus score was 3.70/5 for each method. On the five previously human-reviewed routes, Gemini's focus-fit rating differed from the human rating by 1.20 points on average and its reason-support judgement agreed in 2/5 cases. These are model opinions, not independent ground truth or evidence of superiority. See `evaluation/holdout/RESULTS.md` and `CALIBRATION.md`.

## Live model comparison

With the server running and a key configured:

```sh
npm run evaluate:live
```

This calls the model for the normal cases that have valid candidate sets. It records the selected route, deterministic contract checks, difference from the deterministic top candidate, tokens, provider-reported cost and latency. Unknown cost or an API error stops the run. The script stops before a subsequent call after reported spend reaches $1; this is not a hard provider spending cap. Use a provider key with a suitable spending limit to enforce the $10 project budget.

Successful final-architecture calls are logged in `evaluation/live/route-calls.jsonl`. The evaluator creates `route-comparison.json`, `ROUTE_LIVE_RESULTS.md` and a five-case `route-human-review.json`. The completed review averaged 4.60/5 for request fit and 4.40/5 for training-focus fit; the selection reason was supported in 4/5 cases. N03 exposed an advanced-navigation difficulty-classification weakness. This is a one-reviewer sample without a blinded baseline comparison, so it does not establish model superiority. The later Gemini-generated holdout is separate from these original predefined fixtures and is not an independently human-labelled dataset.

The repository also retains the earlier explanation-only model-judge experiment. It motivated the move to a fixed summary because the hand-labelled template clarity score exceeded the generated explanation score. Those files do not evaluate the final model-selected routes.

## Architecture and boundaries

See `docs/PRODUCT_DOCUMENTATION.md` for the persona, inputs, outputs, box diagram, metrics target versus result, limitations and future path.

- `public/lib/course-engine.js`: graph and constraint engine. Uses only MAP_CANDIDATE edges with `field_verified: true`; filters ineligible/blocked/provisional existing controls, enumerates up to 12 valid candidates, and enforces ±10% distance and all-pairs control spacing. In exploration mode it creates virtual `GPxx` GPS controls on graph nodes I verified. The nearest-node connector limit is 20 m for existing controls.
- `public/lib/retrieval.js`: shared explicit retrieval over eight curated entries. Always includes core feature/safety/distance/spacing rules; adds beginner and route-choice policies when relevant. No vector database or trained model is implied.
- `public/lib/activity-tracker.js`: browser-side GPS filtering, distance accumulation, ordered control-arrival confirmation and GPX generation. It makes no model or server call.
- `src/openrouter.mjs`: bounded JSON route-selection call. The model must return one supplied candidate ID and cannot invent controls.
- `server.mjs`: local-only serving and `/api/generate`; constructs candidates from authoritative local data, sends compact candidates plus RAG evidence to the model, and returns the selected checked route.
- `public/app.js`: model-generation state, map, deterministic checks, field-verification state, fixed-template summary and local activity-recording controls.

A verified result means the generated route stays within paths I verified, uses either eligible existing controls or virtual GPS points on those paths, and passes the encoded distance, spacing and hazard gates. See `public/data/FIELD_VERIFICATION_RECORD.md` for the dated scope and method. My field record is not an independent audit, and temporary construction or weather can still change conditions.

## Data and limitations

288 OSM-derived segments: 238 candidate/field-marked edges and 50 excluded edges. Fourteen eligible control records. Eight curated knowledge records carry source references; project-authored rules are labelled as such.

Path data: © OpenStreetMap contributors, ODbL; https://www.openstreetmap.org/copyright . See `docs/DATA_AND_RISKS.md` for provenance gaps. The map is a prototype inspired by ISSprOM symbols, not a certified competition map. Graph distances include approximate straight connectors from controls to nearby nodes; actual access must be checked. Difficulty and route-choice scoring are heuristics, not validated training-quality measures.

GPS arrival detection is supporting evidence rather than timing-grade proof. Device accuracy, signal obstruction and battery settings can affect the recorded trace and check-ins.
