# Evaluation protocol

## Frozen offline suite

`cases.json` was fixed before the recorded evaluation and its SHA-256 is stored with every run. Twenty normal requests cover distance 600–1400 m, all difficulty/focus categories and 3–5 controls. Ten mutations exercise unavailable paths, blocked controls, missing start/policy/verification, hazards and invalid inputs. The cases are derived from project requirements and boundary scenarios. A separate later holdout generated by another model is documented below.

Normal cases expect either a constraint-valid verified course from the dataset I verified or explicit generation abstention. Edge expectations are fixed in the fixture file. Ground truth here is a behavioural contract, not an independent audit of outdoor access or an expert judgement of training quality.

## Metrics (report separately)

- Verified-course yield: constraint-valid courses using the recorded eligible paths and controls / 20 normal requests. Target: at least 16/20.
- Generation abstention: no feasible route / 20. The result does not prove each rejected case is mathematically infeasible under every possible algorithm.
- Virtual-control validity: every `GPxx` point must lie exactly on a path-network node I verified and pass the same distance, spacing and hazard gates.
- Original full-pass target: at least 16/20 complete verified outputs using the field record I supplied.

## Live model route-selection evaluation

The deterministic engine enumerates up to twelve routes that already satisfy graph connectivity, target-distance tolerance and spacing. The model receives only those candidates, the bounded user request and retrieved rules, then returns one exact candidate ID. The server rejects unknown IDs and derives all metrics and the fixed summary from the selected structured candidate.

`npm run evaluate:live` measures endpoint success, deterministic contract pass rate, provider tokens, cost and latency. It also reports how often the selected route differs from the deterministic top candidate. Difference establishes that the model affected selection, not that the alternative is better.

## Exploration-mode suite

The separate `explore-cases.json` fixture contains six normal requests and four edge cases. Normal cases must generate the requested number of unique virtual `GPxx` controls, place every point exactly on a graph node I verified, satisfy ±10% routed distance and independently measured all-pairs spacing, produce deterministic control order and pass the recorded path and hazard gates. A distinctive physical feature is not required because arrival is coordinate-based. Edge cases remove verified paths, exclude all paths, remove the start or supply an invalid control count; each must abstain. These results are reported separately from the existing-control 16/20 target.
- Contract pass rate: expected behaviour across all 30 cases. This is a regression measure.
- Abstention appropriateness: report prevented invalid outputs on labelled hazard/input cases, and have an independent reviewer classify false abstentions. The current suite supports the first check, not a reliable real-world precision/recall estimate.

A separate haversine calculation checks all-pairs spacing. Eligibility and stated distance tolerance are checked; independent path-distance recomputation and a third-party on-site audit remain outstanding. Do not present contract passes as proof that the route optimiser, map or present physical environment is fully correct.

## Human route-quality review

The reviewer coded `D` completed the five fixed cases in `live/route-human-review.json` using these fields:

- `user_request_fit_1_to_5`: how well the selected distance, difficulty and requested control count fit the request;
- `training_focus_fit_1_to_5`: how well the selected features support navigation, route-choice or physical training;
- `selection_reason_supported`: whether the cited reason follows from the retrieved rules and selected features.

The reproducible summary is generated with `npm run evaluate:route-human`. It reports the means with sample size and the failed case rather than converting five cases into a generalisation claim. The result was 4.60/5 mean request fit, 4.40/5 mean training-focus fit and 4/5 supported selection reasons; N03 was the notable failure. The older explanation comparison and model-judge calibration remain in `live/` as iteration evidence because they motivated the fixed-template summary; they are not final-route performance.

## Different-model holdout and calibration

Gemini 2.5 Flash generated twenty requests without seeing the original cases or route results. `holdout/cases.json` was frozen before running the production selector and its SHA-256 recorded in `holdout/generation-metadata.json`. For each request, the runner records whether a route was generated and checks unique eligible controls, path/control/hazard gates in my field record, independently calculated all-pairs spacing and ±10% distance. It also compares the model-selected route with the deterministic top candidate. Only differing pairs are sent to Gemini with A/B order alternated and route origin hidden. Gemini scores request and focus fit and chooses a preference or tie. The five existing human-reviewed routes are separately scored by Gemini without disclosing the human ratings to it; score differences and reason-support agreement are reported.

The holdout tests generalisation to unseen request combinations, not physical reachability ground truth. The model judge's ratings are opinions, and its five-case calibration showed imperfect agreement with human review. It cannot establish route superiority. Obtain independently human-labelled cases and blinded human baseline comparisons for stronger claims. Do not silently tune the frozen cases after seeing failures.
